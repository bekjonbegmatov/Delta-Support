# 🛠️ AI Tool Calling: действия через Support API

AI не только читает данные клиента — он умеет **выполнять действия** на стороне вашего сервиса: проверить платёж, посмотреть устройства подписки, при необходимости сбросить их или перевыпустить подписку. Это отдельный уровень поверх обычной интеграции из [docs/INTEGRATION_BACKUP.md](INTEGRATION_BACKUP.md).

## Модель безопасности: коротко

AI может ошибиться или быть обманут («напиши в чат от имени другого клиента» — классическая попытка prompt injection). Поэтому границы жёсткие и **не зависят от того, что решил сказать AI**:

- **Read-only** действия (проверка платежа, инфо о подписке) AI вызывает автономно во время обычного разговора с клиентом — но каждый вызов сверяется с реальными данными **этого конкретного** Telegram-чата на сервере, а не с тем, что AI написал в параметрах
- **Разрушающие** действия (сброс устройств, перевыпуск подписки) AI никогда не выполняет напрямую — только формирует предложение, реальный вызов Support API происходит исключительно после клика клиента по кнопке подтверждения в Telegram, с повторной проверкой владения в момент клика

## Read-only инструменты

| Инструмент | Когда AI его вызывает | Что проверяется |
|---|---|---|
| `check_payment` | Клиент говорит, что оплатил, но деньги не пришли, или спрашивает статус платежа | Ответ Support API содержит `user.telegram_id` — если он не совпадает с telegram_id текущего чата, AI получает «транзакция не найдена», а не чужие данные |
| `get_subscription_info` | Нужны детали конкретной подписки клиента (тариф, срок, трафик, лимит устройств) | `username` подписки ищется среди **собственных** подписок клиента (из уже загруженных данных аккаунта) — если не найдено, AI получает «подписка не найдена среди подписок этого клиента» |
| `get_subscription_devices` | Клиент спрашивает, какие устройства подключены | Та же проверка владения, что и у `get_subscription_info` |

AI получает результат вызова как обычные данные и сам формулирует ответ клиенту — никакого отдельного UI для этого не нужно, всё происходит прямо в переписке.

## Разрушающие инструменты и подтверждение

| Инструмент | Что делает | Ограничение |
|---|---|---|
| `reset_devices` | Отключает **все** устройства подписки, нужна новая привязка | — |
| `revoke_subscription` | Перевыпускает подписку (новая ссылка, старые устройства отключаются) | Работает только если с даты выдачи подписки прошло больше 20 дней — иначе Support API вернёт `subscription_too_new`, и клиент увидит, сколько дней осталось ждать |
| `delete_device` | Удаляет одно конкретное устройство по `hwid` | Обычно вызывается после `get_subscription_devices`, когда клиент указал, какое устройство убрать |

Когда AI решает, что нужно одно из этих действий, происходит следующее:

1. Сервер проверяет владение (см. ниже) — если подписка не найдена среди подписок этого клиента, AI получает отказ и объясняет это клиенту, **никакого запроса на подтверждение не создаётся**
2. Если владение подтверждено — клиенту приходит сообщение с текстом действия и двумя кнопками: **✅ Да, подтверждаю** / **❌ Отмена**
3. Реальный вызов Support API происходит только по клику «Подтверждаю» — и владение **проверяется ещё раз** в этот момент (защита от гонок и просроченных данных)
4. Кнопки одноразовые: повторный клик или клик другого пользователя ничего не делает («действие устарело» / «это не для вас»)
5. Токен подтверждения живёт 5 минут (Redis, либо память процесса как fallback, если Redis недоступен)

Это значит, что диалог выглядит примерно так:

```
Клиент: сбросьте все мои устройства, хочу переустановить

AI: ⚠️ Точно сбросить ВСЕ устройства подписки «Premium»? Все подключённые
    устройства отключатся, их нужно будет подключить заново.
    [✅ Да, подтверждаю]  [❌ Отмена]

Клиент: *нажимает «Да, подтверждаю»*

Бот: ✅ Все устройства подписки сброшены.
```

## Как проверяется владение

Единственная точка проверки — `find_own_subscription()` в `modules/user_info.py`. Она берёт **уже загруженные и закешированные** данные аккаунта конкретного `telegram_id` (те же, что видит AI в блоке `{account_info}` промпта) и ищет среди них подписку с указанным `username`/`short_id`.

Принципиально: сервер никогда не доверяет идентификатору, который AI взял из своих аргументов вызова, «просто потому что AI так решил» — совпадение всегда сверяется с реальным списком подписок этого telegram_id, полученным напрямую от Support API. Даже если prompt injection заставит модель попытаться подставить чужой `username` — сервер найдёт, что такой подписки у этого клиента нет, и откажет.

## Контракт Support API

Для действий бот обращается к тем же базовому URL и токену, что настроены в [Интеграции](INTEGRATION_BACKUP.md), к дополнительным путям:

| Метод | Путь | Тело запроса | Назначение |
|---|---|---|---|
| POST | `/api/support/subscription_info` | `{"username": "..."}` или `{"short_id": "..."}` | Подробности подписки |
| POST | `/api/support/subscription/devices` | `{"username": "..."}` | Список устройств подписки |
| POST | `/api/support/subscription/device/delete` | `{"username": "...", "hwid": "..."}` | Удалить одно устройство |
| POST | `/api/support/subscription/devices/reset` | `{"short_id": "..."}` | Сбросить все устройства |
| POST | `/api/support/subscription/revoke` | `{"username": "..."}` | Перевыпустить подписку (только если возраст ≥ 20 дней) |
| POST | `/api/support/payment/check` | `{"transaction_id": "..."}` | Статус платежа по ID/order_id |

Авторизация та же, что у `user_info` — заголовок `Authorization: Bearer sup_...`. Ответы — JSON с полем `"ok": true/false`; при `false` — `"error"` с кодом (например `subscription_too_new`, `user_not_found`).

Если ваш Support API-сервер ещё не реализует какие-то из этих путей — соответствующий инструмент просто будет возвращать ошибку, AI объяснит клиенту, что действие недоступно, и предложит менеджера. Ничего не сломается из-за отсутствующего эндпоинта.

Полная спецификация всех эндпоинтов с точными примерами запросов и ответов (включая `user_info`) — [docs/SUPPORT_API_SPEC.md](SUPPORT_API_SPEC.md).

## Как это всё связано с фото и голосовыми

Tool calling работает и в обычном текстовом диалоге, и после того как голосовое сообщение расшифровано в текст (Whisper) — с точки зрения AI это одно и то же: текстовый вопрос клиента с доступными инструментами. При обработке фото и документов-картинок инструменты также доступны: AI может прочитать ошибку и проверить данные клиента в том же запросе. Подробности — [docs/AI_PROVIDERS.md](AI_PROVIDERS.md#vision-модели-распознавание-фото).

## Настройка

Отдельных переключателей для tool calling нет — он включается автоматически, как только:
1. [Support API подключён](INTEGRATION_BACKUP.md#настройка-подключения) (`Включено` + URL + токен)
2. Есть хотя бы один активный [AI-провайдер](AI_PROVIDERS.md)

Если Support API выключен, инструменты аккаунта недоступны; AI использует базу знаний, общий контекст и локальные инструменты поддержки.


## Многошаговая диагностика и локальные инструменты

AI может последовательно вызвать инструменты: например, сначала получить подписку, затем её устройства. На один ответ допускается до шести раундов инструментов, затем запрос финального текста; одинаковый вызов повторно не исполняется в пределах ответа. Неизвестные инструменты и некорректные JSON-аргументы отклоняются.

`offer_manager` предлагает кнопку без автоматического приглашения человека. Причины: прямая просьба клиента, конкретное действие вне полномочий AI или неудачная диагностика после предыдущих ответов. Само слово «подключить» или «менеджер» больше не включает кнопку.

`report_knowledge_gap` записывает недостающую тему в [предложения базы знаний](KNOWLEDGE_BASE.md). Эти два локальных инструмента работают и без внешней интеграции аккаунтов. Управляющие действия по-прежнему требуют кнопки подтверждения и серверной проверки владельца.
