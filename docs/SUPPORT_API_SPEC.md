# 📡 Спецификация Support API

Это контракт для сервера, который бот вызывает, чтобы получать данные о клиенте и выполнять действия с его подпиской. Если у вас есть свой backend (например, панель управления VPN-сервисом) — реализуйте эти эндпоинты, и интеграция из [docs/INTEGRATION_BACKUP.md](INTEGRATION_BACKUP.md) заработает.

Как бот использует эти данные: [docs/AI_TOOL_CALLING.md](AI_TOOL_CALLING.md).

> 📌 **Примечание:** скоро появится готовая интеграция с Bedolaga — реализовывать эту спецификацию вручную для проектов на этой панели не понадобится.

## Авторизация

Все ручки принимают токен поддержки через заголовок:

```
Authorization: Bearer sup_xxx
Content-Type: application/json
```

Токен хранится на сервере поддержки и не передаётся клиенту, браузеру или AI в аргументах инструмента. Для запросов используется заголовок `Authorization`, а не URL или тело.

Если токен неверный, любой эндпоинт должен вернуть:

```json
{"ok": false, "error": "invalid_token"}
```

Базовый URL — тот, что указан в панели (Настройки → Интеграция и бэкап), например `https://example.com`. Все пути ниже — относительно него. Хвостовой слэш допускается (`/api/support/user_info/` работает так же, как без слэша).

## 2. Подробная информация о подписке

Искать можно по `username` подписки (из `connections.remna_subscriptions[].username`) либо по `subscription_id` — её локальному ID.

**`GET /api/support/subscription_info?username=46235_41nr3`**

Альтернативный query-параметр: `subscription_id=42`.

`display_name` — уникальный код подписки Remnawave, равный её `username`. В списках, кнопках и подтверждениях показывается `display_name`, а для старых ответов — `username`. Название тарифа `tarif` отображается отдельно: оно не уникально и не используется для выбора подписки. `user.username` — Telegram username владельца, он также не является кодом подписки.

Выбранная подписка сохраняется с её `username` и `id`; операции повторно проверяют принадлежность этого выбора клиенту. Если ни `display_name`, ни `username` не пришли, тариф не подставляется вместо идентификатора; запрос возможен только по проверенному локальному `subscription_id`.

Ответ:

## 6. Перевыпустить подписку

`revoke` перевыпускает ссылку и отключает старые подключения. Это не продление срока подписки.

Работает только если с даты выдачи подписки прошло больше 20 дней — это ограничение должно быть реализовано на стороне сервера (бот сам его не проверяет, только показывает клиенту то, что вернул сервер).

**`POST /api/support/subscription/revoke`**

Запрос:
```json
{"username": "46235_41nr3"}
```

Успешный ответ:
```json
{
  "ok": true,
  "revoked": true,
  "age_days": 25,
  "note": "Ссылка подписки перевыпущена, но support API её не возвращает."
}
```

Если рано:
```json
{
  "ok": false,
  "error": "subscription_too_new",
  "age_days": 8,
  "required_age_days": 21
}
```

Бот использует `age_days`/`required_age_days` из ответа, чтобы сказать клиенту, сколько ещё ждать — считайте эти поля обязательными при отказе по этой причине.

## 7. Проверить платёж

Можно передать `order_id`, provider transaction id, или числовой `Transaction.id` — сервер сам разбирается, что это за идентификатор.

**`GET /api/support/payment/check?transaction_id=05dcc027-3b02-44e9-8093-70245eeeab50`**

После создания счёта для проверки используется `order_id` (либо `transaction_id`, если он указан в ответе). Этот endpoint возвращает актуальный статус. Статус из повторного ответа создания — сохранённый снимок; переход по ссылке и возврат с платёжной страницы оплату не подтверждают.

Ответ:
```json
{
  "ok": true,
  "transaction": {
    "id": 123,
    "method": "platega_crypto",
    "method_label": "Platega криптовалюта",
    "summa": "100.00",
    "status": true,
    "order_id": "3a20efb1-916d-4683-91dd-46b543d83420",
    "provider_transaction_id": "05dcc027-3b02-44e9-8093-70245eeeab50",
    "created": "2026-08-04T10:00:00+08:00",
    "processed_at": "2026-08-04T10:02:00+08:00"
  },
  "user": {
    "telegram_id": 5163141099,
    "balance": "150.00"
  }
}
```

**Важно:** `user.telegram_id` обязателен и здесь — иначе бот не сможет проверить, что клиент не пытается узнать статус чужого платежа по угаданному/подсмотренному ID.

## 8. Создать ссылку пополнения

**`POST /api/support/payment/create`**

Заголовки:
```text
Authorization: Bearer <SUPPORT_TOKEN>
Idempotency-Key: <UUID>
Content-Type: application/json
```

Тело:
```json
{
  "user_id": 123456789,
  "method": "platega_sbp",
  "amount": 2000
}
```

`user_id` — Telegram ID клиента. AI подготавливает предложение счёта; новый UUID создаётся сервером только после отдельного явного подтверждения клиентом кнопкой «Создать новый счёт». Операция, ключ и параметры сохраняются в БД до HTTP-запроса. При повторе одного запроса сохраняются ключ и все параметры; повтор успешного запроса возвращает сохранённый ответ без второго счёта. Для оплаты используется `pay_link`; `order_id`/`transaction_id` сохраняются для отдельного запроса актуального статуса.

| HTTP | Код | Значение |
|---|---|---|
| 409 | `operation_requires_review` | Операция с этим ключом ещё выполняется или требует проверки |
| 409 | `idempotency_conflict` | Ключ уже использован с другими параметрами или другим Support-токеном |
| 502 | `checkout_uncertain` | Результат создания счёта неизвестен |

После таймаута, HTTP 502 или 409 интеграция не создаёт новый ключ автоматически. Повтор того же запроса использует прежний UUID и параметры. Новый счёт разрешён только по отдельному явному действию клиента. Предыдущие операции и счета не удаляются и не отменяются автоматически.

Предыдущие операции `running`/`uncertain` не блокируют отдельный новый запрос с новым ключом; ошибка `previous_operation_requires_review` больше не является основанием для такой блокировки. Несколько счетов могут быть оплачены, каждый подтверждённый платёж учитывается отдельно.

Для Platega бэкенд сам заполняет `metadata.user_email` значением `<telegram_id>@telegram.org`. Интеграция не запрашивает email клиента и не передаёт `metadata` в Support API.

## Общие правила

- Для управляющих операций с подпиской передаётся её `username` либо `subscription_id`; для удаления одного устройства дополнительно `hwid`. Проверка владения и подтверждение клиента сохраняются.
- Все эндпоинты возвращают `"ok": true/false` — при `false` обязательно поле `"error"` с машиночитаемым кодом
- Даты — ISO 8601 со смещением таймзоны (`+08:00` и т.п.)
- Денежные суммы в информационных ответах могут быть строками (`"250.00"`); `amount` при создании счёта передаётся целым числом рублей
- Любой эндпоинт, отдающий данные конкретного пользователя (`user_info`, `subscription_info`, `payment/check`), должен включать `telegram_id` в ответе — это единственный способ для бота проверить, что данные принадлежат тому, кто спрашивает
- Если какой-то из эндпоинтов действий (2–6) у вас пока не реализован — ничего страшного: соответствующий инструмент AI просто вернёт ошибку, бот предложит клиенту менеджера. Реализуйте по мере необходимости, начиная с `user_info` — это единственный обязательный минимум
